# Аудит исходного кода

Список составлен по коду и **проверен на живом стенде**. У каждого пункта: где, чем грозит,
что делаем. Колонка «Проверено» — как факт подтверждён: `стенд` (воспроизведено руками,
детали в [behaviour.md](behaviour.md)), `код` (следует из чтения кода), `сборка` (видно при
`docker compose build`).

Порядок исправления — по этапам плана; номера пунктов (A1, Б3, И2…) используются в сообщениях
коммитов и в README, чтобы правку можно было найти по номеру.

## Б. Архитектура

| # | Что не так | Чем грозит | Что делаем |

## В. Производительность

Полный разбор кандидатов на «неочевидную оптимизацию» — на этапе 4; здесь сводка.

| # | Где | Что не так | Подтверждение |
|---|---|---|---|
| В1 | `service.py:54`, `tasks.py:75,79` | Функции объявлены `async`, но внутри синхронный файловый ввод-вывод: `write_bytes`, `read_text`, `read_bytes`. Каждый такой вызов блокирует event loop целиком | стенд: `GET /files` под восемью параллельными загрузками по 20 МБ — max 0.009 s → **1.715 s** |
| В2 | `service.py:46,54`, `tasks.py:75,79` | `await upload_file.read()` держит файл в памяти целиком, `write_bytes` дублирует его же, а `_extract_file_metadata` читает тот же файл заново | код: пик памяти — два-три размера файла на каждую параллельную загрузку, при отсутствии лимита размера (A10) |
| В3 | `tasks.py:13-23` | `create_async_engine` вызывается на импорте, то есть в родительском процессе Celery до `fork`; пул asyncpg привязан к event loop и форк не переживает. | В4 | `tasks.py` целиком | Цепочка из трёх задач: три постановки в очередь, три сессии БД, три `session.get` одной и той же строки, два чтения одного файла. Между задачами передаётся только `file_id` | код |
