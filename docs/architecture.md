# Целевая архитектура бэкенда

Документ описывает, куда переезжает код и почему именно так. Он написан **до** рефакторинга,
чтобы правило зависимостей задавалось решением, а не получалось само собой.

Отправная точка — четыре файла на 350 строк, в которых смешаны конфигурация, доступ к данным,
работа с диском, бизнес-правила и HTTP. Подробности — в [audit.md](audit.md), группа Б.

## Правило зависимостей

```
api  →  services  →  repositories  →  models
              ↘         ↘
             domain    storage
```

Стрелка — «знает о». Правило одно, и оно проверяемо чтением импортов:

1. **`domain/` не импортирует ничего из проекта.** Ни FastAPI, ни SQLAlchemy, ни Celery, ни
   `pathlib` для чтения файлов. Только стандартная библиотека и pydantic-модели результата.
2. **`repositories/` знает про `models/` и сессию SQLAlchemy** — и больше ни про что. Никаких
   `HTTPException`: не нашли — вернули `None`.
3. **`services/` оркестрируют**: дёргают репозитории, домен и хранилище, владеют транзакцией и
   бросают доменные исключения. Про HTTP не знают.
4. **`api/` — единственное место, где живёт HTTP.** Роутеры, схемы запроса и ответа, и
   `errors.py`, который переводит доменное исключение в код ответа.
5. **`worker/` — такой же клиент сервисов, как `api/`.** Задача Celery разбирает аргументы,
   открывает сессию и вызывает тот же сценарий, что и HTTP-эндпоинт.

Обратных стрелок нет: `services` не импортирует `api`, `domain` не импортирует `services`.
Это то, что сейчас нарушено сильнее всего — `service.py` бросает `HTTPException`, то есть
бизнес-логика зависит от веб-фреймворка и не может быть вызвана из воркера без него.

## Структура

```
backend/src/
├── main.py                  # сборка приложения: роутеры, middleware, lifespan
├── core/
│   ├── config.py            # pydantic-settings: БД, брокер, хранилище, лимиты — из env, с валидацией
│   ├── db.py                # движок, sessionmaker, зависимость get_session
│   ├── logging.py           # структурные логи
│   └── exceptions.py        # доменные ошибки: FileNotFound, EmptyFile, FileTooLarge, StoredFileMissing
├── api/
│   ├── deps.py              # DI: сессия, сервисы, хранилище
│   ├── errors.py            # доменная ошибка → HTTP-код, единственное место с HTTP-семантикой
│   └── v1/
│       ├── files.py         # эндпоинты файлов
│       └── alerts.py        # эндпоинты алертов
├── domain/
│   ├── enums.py             # ProcessingStatus, ScanStatus, AlertLevel
│   ├── scanner.py           # правила детекта — чистые функции
│   └── metadata.py          # извлечение метаданных — чистые функции над потоком байтов
├── models/                  # ORM: file.py, alert.py
├── schemas/                 # pydantic: запросы и ответы, отдельно от ORM
├── repositories/            # file_repository.py, alert_repository.py — только запросы
├── services/                # file_service.py, alert_service.py — сценарии и транзакции
├── storage/                 # протокол FileStorage и LocalFileStorage
└── worker/
    ├── celery_app.py        # конфигурация Celery, инициализация ресурсов на worker_process_init
    └── tasks.py             # тонкие задачи: разобрать аргументы, вызвать сервис
```

## Почему именно эти границы

**`domain/` отдельно от всего остального — главное решение.** Сейчас правила детекта угроз
(список расширений, порог 10 МБ, сверка расширения с mime) лежат внутри тела celery-задачи:
чтобы проверить, что `.exe` помечается подозрительным, нужно поднять Redis, Postgres, положить
файл на диск и дождаться воркера. После выноса это функция
`scan(name, size, media_type, head) -> ScanResult` без единого внешнего вызова, и таблица
«вход → выход» из [behaviour.md](behaviour.md) ложится в `pytest.mark.parametrize` строка в
строку. Это и есть проверяемый ответ на «предложите своё видение»: границу проводим там, где
она даёт тесты за секунды и без докера.

**`repositories/` отдельно от `services/`** нужны ровно за тем, чтобы сценарий можно было
прочитать целиком. Сейчас `delete_file` — это одновременно поиск записи, HTTP-404, удаление
файла с диска и коммит; понять порядок операций (и то, что он неверный, см. A8) можно только
вглядываясь. Когда репозиторий отвечает лишь на вопрос «дай запись по id», в сервисе остаётся
последовательность шагов, и ошибочный порядок становится виден глазами.

**`storage/` за протоколом** — потому что «локальная папка» здесь не архитектура, а совпадение:
в dev воркер видит загруженный файл только потому, что оба контейнера монтируют один и тот же
`./backend` (Б4). Протокол `FileStorage` (`save`, `open`, `delete`, `exists`) делает это
явным: локальная реализация остаётся, но подмена на S3 — это новый класс, а не правка
сервисов. Тот же интерфейс закрывает В1 и В2 — потоковое сохранение живёт внутри реализации,
сервису об этом знать не нужно.

**`worker/` рядом с `api/`, а не под ним.** Оба — точки входа, оба вызывают одни и те же
сценарии. Сегодня задача Celery делает всю работу сама: сама открывает сессию, сама
применяет правила, сама пишет алерт. После переноса задача становится тонкой, а сценарий
`process_file` можно вызвать в тесте напрямую, синхронно, без брокера.

**Транзакция — на сценарий, а не на функцию.** Сессия приходит через зависимость (`Depends` в
API, явное открытие в задаче), а не создаётся внутри каждой функции. Именно это сейчас делает
невозможным «сохранить файл и записать алерт одной транзакцией» и требует живой БД для любого
теста (Б2).

## Что осознанно не делаем

Тестовое легко превратить в витрину паттернов, поэтому граница проведена и с этой стороны:

- **Нет отдельного Unit of Work.** Сессия SQLAlchemy уже им является: `flush`, `commit`,
  `rollback` и identity map — это и есть UoW. Обёртка сверху добавила бы слой без единого
  нового свойства.
- **Нет CQRS и шины событий.** Четыре эндпоинта и один линейный конвейер. Разделение команд и
  запросов окупается, когда у чтения и записи разные модели или разные нагрузки; здесь нет ни
  того, ни другого.
- **Нет мапперов «ORM → доменная сущность → DTO».** Достаточно двух представлений: ORM-модель
  и pydantic-схема ответа. Третье промежуточное только добавило бы места, где данные
  расходятся.
- **Нет микросервисов.** Воркер и так отдельный процесс со своим масштабированием — это и есть
  та граница, которая здесь нужна.
- **Нет репозитория-абстракции над Celery.** Задача и есть точка входа; прятать её за
  интерфейсом «на случай смены брокера» — гадание.

Общее правило: слой появляется, когда у него есть **своя причина меняться**. `domain/`
меняется, когда меняются правила безопасности; `storage/` — когда переезжаем в облако;
`api/` — когда меняется контракт. Слой, который меняется всегда вместе с соседним, — лишний.

## Как это проверяется

Правило зависимостей — не декларация, у него есть наблюдаемые следствия:

- в `domain/` нет ни одного импорта `fastapi`, `sqlalchemy`, `celery` (проверяется грепом и
  тестом, который импортирует модуль в чистом окружении);
- юнит-тесты на `domain/scanner.py` и `domain/metadata.py` проходят без докера, БД и брокера;
- `HTTPException` встречается только в `api/`;
- сценарий `process_file` вызывается из теста напрямую, без Celery.

Целевая структура фронтенда описана отдельно — она появится в этом же каталоге на этапе слоёв
фронта.
