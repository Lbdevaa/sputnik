# Слои фронтенда

Исходная точка — один `page.tsx` на 367 строк: типы, форматтеры, вызовы API, состояние,
две таблицы и модальное окно в одном компоненте (Г1). Подробности — в [audit.md](audit.md),
группа Г.

## Раскладка

Feature-Sliced Design без догматизма: на одну страницу полноценный FSD с `pages/` и
`processes/` избыточен, но само деление на слои с односторонними зависимостями — ровно то,
что нужно, чтобы таблицу, форму и http-клиент можно было менять и проверять по отдельности.

```
frontend/src/
├── app/                     # Next: layout, page (только композиция), error, loading, favicon
├── shared/                  # ничего не знает о предметной области
│   ├── api/                 # http-клиент: базовый URL из env, ApiError, разбор detail
│   ├── config/              # env, интервал опроса, размеры страниц
│   ├── lib/                 # formatDate/formatSize, сортировка и фильтр, useQuery, usePagedQuery
│   └── ui/                  # DataTable, TablePagination, SectionCard, ErrorBanner
├── entities/
│   ├── file/                # тип FileItem, статусы как union, API файлов, useFiles, колонки
│   └── alert/               # тип AlertItem, уровни, API алертов, useAlerts, колонки
├── features/
│   ├── upload-file/         # модальное окно с формой, своим состоянием и своей ошибкой
│   ├── delete-file/         # кнопка удаления с подтверждением
│   └── refresh-data/        # кнопка «Обновить»
└── widgets/
    ├── files-table/         # карточка «Файлы»: DataTable + действия по строке
    └── alerts-table/        # карточка «Алерты»
```

## Правило зависимостей

```
app → widgets → features → entities → shared
```

Стрелка — «импортирует». Обратных стрелок нет, и это не договорённость, а правило ESLint:
`no-restricted-imports` в `eslint.config.mjs` запрещает `shared/` знать про слои выше,
`entities/` — про `features/` и `widgets/`, и так далее. Нарушение — красный `npm run lint`.

Внутри слоя срез общается с соседями только через свой `index.ts`: `@/entities/file`, а не
`@/entities/file/model/status`.

## Что и почему

**Опрос статусов, пока есть файлы в работе (Г3).** Обработка асинхронная: файл появляется как
`uploaded`, через секунды становится `processing`, затем `processed`, и только тогда возникает
алерт. Исходный интерфейс узнавал об этом по кнопке «Обновить». Теперь `useFiles` включает
опрос раз в три секунды, пока на странице есть хотя бы один файл в статусе `uploaded` или
`processing`, и выключает, когда все обработаны; алерты опрашиваются по тому же признаку,
потому что появляются в конце конвейера. Опрос не идёт на скрытой вкладке. Пока он активен,
рядом с заголовком карточки горит «● live».

**Отмена запросов (Г6).** `useQuery` держит `AbortController`: новый запрос отменяет
предыдущий, размонтирование — текущий. С опросом это не косметика: без отмены ответ на
старый запрос мог бы перезаписать более свежие данные.

**Первая загрузка и фоновое обновление — разные состояния.** Спиннер показывается только пока
данных нет вообще; опрос и «Обновить» обновляют таблицу на месте, не моргая.

**«Ожидает», а не «чисто» (Г4).** До проверки бейдж нейтральный серый с подписью «Проверка
ещё не выполнялась». Раньше цвет выбирался по `requires_attention`, и необработанный файл
светился зелёным.

**Ошибка формы внутри формы (Г5).** У модального окна загрузки своё состояние и своя
ошибка; баннер страницы — только для действий на странице (удаление) и ошибок загрузки
списков, и у него есть «Повторить».

**Таблица для большого объёма данных (Г10).** Общий `DataTable` с сортировкой по колонке
(по кругу: по возрастанию → по убыванию → без), поиском и пагинацией. Пагинация —
серверная, через `limit/offset` бэкенда; сортировка и поиск — над загруженной страницей,
и подвал таблицы прямо говорит «показано N из M на странице», чтобы пустой результат поиска
не читался как «в базе нет». Следующий шаг, если понадобится, — `sort` и `q` на бэкенде;
контракт таблицы от этого не изменится.

**Статусы — union-типы (Б5).** `ProcessingStatus`, `ScanStatus`, `AlertLevel` объявлены
через `as const` и совпадают с перечислениями бэкенда; словари подписей и вариантов бейджей
типизированы как `Record<Status, …>`, так что новый статус на бэкенде без пары на фронте —
ошибка компиляции, а не серый бейдж без названия.

**Один форматтер дат на модуль (Г7)**, `NEXT_PUBLIC_API_URL` вместо трёх захардкоженных
адресов (Г2), иконка в `src/app/favicon.ico`, чтобы Next сам выставил путь с учётом
`basePath` (A12).

## Инструменты

- `strict: true` и `noUncheckedIndexedAccess` в `tsconfig.json` (Г9).
- ESLint 9 с конфигурацией Next и правилами слоёв, Prettier.
- Vitest на чистые функции: форматтеры, сортировка и фильтр, представление статусов, уровни
  алертов. Компонентные тесты через Testing Library и e2e через Playwright легли бы поверх;
  для тестового они не окупаются.
- Версии в `package.json` зафиксированы точно (Г8): `next: latest` в исходнике означал, что
  сборка сегодня и сборка завтра — разные сборки.

```
cd frontend
npm ci
npm run check      # typecheck + lint + format:check + test
```
